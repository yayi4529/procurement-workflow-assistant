# Task06-B 多采购项工作流与 Agent 集成

## 范围

Task06-B 在 Task06-A 数据模型上完成多采购项的可操作链路，不新增核心业务表。采购单
包含请求头和多个活动采购项；每个采购项独立形成审核快照、采购执行和零到多条收货
记录。后端详情中的 `request_fulfillment` 是唯一正式履约汇总。

## 文本 Agent 边界

申请人可以用文本 Agent 维护草稿：整体替换、修改请求头、新增、修改和移除采购项。
每项使用会话内稳定的 `draft_item_id`，保存后同时保留后端 `request_item_id`。关联 Task05
资产时必须先由后端校验资产引用。Agent 只写 `DRAFT`，不得提交审核或执行任何正式
状态流转；用户不知道买什么时只能澄清需求或查询资产，不能做故障诊断。

## 确定性卡片链路

```text
申请人确认整单及明细
→ 楼长按采购项保存审核快照并提交采购员
→ 采购员逐项登记供应商与成交信息
→ 全部采购项已有执行记录后提交仓库
→ 仓库按执行记录追加部分/最终收货
→ 后端汇总全部需入库项后确认完成
```

纯服务采购项不显示收货入口。整单全部为服务项时，采购员确认后由后端直接完成，
`assigned_to_employee_id` 为空。混合采购单仍由仓库处理需要入库的采购项。

## 一致性与安全

- 读取和判断以最新后端详情、`allowed_actions`、当前处理人和版本为准。
- 保存携带 `expected_version`；正式动作及逐项采购、追加收货携带稳定 `action_token`。
- 重复逐项采购返回 `ITEM_ALREADY_PURCHASED`，重复 token 按操作日志幂等处理。
- 累计收货由后端锁定执行记录后校验；超过采购数量返回 `OVER_RECEIPT`。
- 供应商黑名单由后端在采购执行时校验，客户端提示不能替代该约束。
- 移除草稿项采用后端软失活语义，历史审核、执行和收货记录不被客户端删除。
- 跨角色通知只来自后端 Outbox，可附简短项目数与项目摘要。

## 兼容性

旧版单采购项字段接口继续作为单项兼容桥。多采购项卡片不展示整单采购字段入口，
避免把多项数据压平。旧状态枚举和七阶段工作流保持不变。

## 验证

根项目执行格式、静态检查、类型检查、全部 pytest 和 diff 检查。后端数据库测试还需
本地 MySQL/Redis/Docker 环境可用；环境不可用时应单独报告阻塞，不得编造结果。
